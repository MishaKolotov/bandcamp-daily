# bandcamp-daily

Каждый день подбирает по свежему и по архивному релизу в четырёх жанрах —
crust, death metal, hardcore punk, black metal — на основе личной коллекции
Bandcamp-фаната `gigamike666`, присылает кандидатов владельцу в личку
Telegram на апрув и по кнопке «📢 В канал» публикует их в один из четырёх
каналов (`CRUST DAILY`, `DEATH METAL DAILY`, `HARDCORE PUNK DAILY`,
`BLACK METAL DAILY`).

Node 20, TypeScript через `tsx` (без шага сборки), `node:test`, `fetch` из
стандартной библиотеки. Внешних рантайм-зависимостей нет. Всё состояние —
JSON-файлы в `data/`, коммитятся в репозиторий самими джобами.

## Как это устроено

Три точки входа, три разных ритма:

| Скрипт | Когда | Кто запускает |
|---|---|---|
| `bin/build-profile.ts` | разово, и дальше только когда вкус ощутимо меняется | владелец руками |
| `bin/neighbors.ts` | раз в неделю | `.github/workflows/neighbors-weekly.yml` |
| `bin/daily.ts` | раз в день | `.github/workflows/daily.yml` |

### `bin/build-profile.ts` — профиль вкуса (разово, руками)

Читает коллекцию и вишлист владельца на Bandcamp (~720 страниц релизов),
считает вес каждого тега в каждом из четырёх бакетов и антипрофиль
(стоп-теги — то, что типично для соседних жанров, но не встречается в
коллекции). Пишет `data/profile.json` и `data/location-vocabulary.json`.

Холодный прогон — 20–40 минут (страницы релизов кэшируются на диск в
`.cache/` навсегда, повторный прогон почти мгновенный). Не запускается по
расписанию — считается, что вкус не меняется настолько быстро, чтобы
пересобирать профиль чаще, чем руками, по необходимости:

```bash
npm run build-profile           # откажется перезаписать существующий profile.json
npm run build-profile -- --force            # пересобрать профиль, затерев ручные правки
npm run build-profile -- --force-locations  # пересобрать ещё и словарь мест (редко нужно)
```

Скрипт печатает по каждому бакету число релизов, число тегов, переживших
порог, и число найденных стоп-тегов — если бакет получился тонким, это видно
сразу в выводе, а не через месяц по качеству подборок.

### `bin/neighbors.ts` — соседи по вкусу (еженедельно)

Строит граф: кто ещё на Bandcamp покупает то же, что и владелец, и что из
их коллекций владелец пропустил. Результат — `data/neighbors.json`, вход
для «архивной» половины ежедневных подборок. Не читает страницы релизов
вообще (только JSON API коллекций и покупателей) — не пользуется дисковым
кэшем `.cache/`.

Как и `build-profile`, отказывается перезаписать существующий файл без
`--force` при локальном запуске — CI-workflow передаёт `--force` явно (см.
ниже), иначе он падал бы каждую неделю начиная со второй.

```bash
npm run neighbors               # первый прогон, файла ещё нет
npm run neighbors -- --force    # пересчитать поверх существующего
```

### `bin/daily.ts` — ежедневный запуск

1. Разбирает нажатия кнопок, накопившиеся с прошлого раза (`data/state.json`).
2. Чистит личку: сносит всё, что осталось от прошлых прогонов — карточки, на
   которые владелец так и не нажал, и служебные уведомления. Снесённая
   карточка считается показанной (её URL уходит в `seen`), так что тот же
   релиз не придёт завтра заново.
3. Собирает кандидатов по четырём бакетам: свежак — из тег-хабов Discover и
   из дискографий 166 подписок владельца; архив — топ голосов соседей
   (`data/neighbors.json`), которых владелец ещё не видел.
4. Присылает карточки владельцу в личку с тремя кнопками: **📢 В канал**
   (публикует в канал бакета), **⏭ Скип** (штрафует теги релиза —
   накапливается в `feedbackTags`), **🔄 Другой** (следующий кандидат из
   запаса).
5. Ждёт нажатий примерно `LISTEN_MINUTES` (по умолчанию 120) и выходит,
   сохранив состояние. Что осталось без ответа — с живыми кнопками, следующий
   запуск разберёт нажатие через дренаж backlog на шаге 1, а потом снесёт
   карточку на шаге 2.

Разобранная карточка (опубликована / скипнута / кандидаты кончились) **сразу
удаляется** из лички, а не дожёвывается в «закрытую» с припиской. Обратная
связь — всплывашка на кнопке, она исчезает сама. Смысл простой: в личке в
любой момент лежит ровно то, что ещё надо послушать, и ничего больше.

```bash
LISTEN_MINUTES=3 npm run daily   # короткое окно для ручной проверки
```

## Файлы данных (`data/*.json`)

| Файл | Кто пишет | Хозяин | Что внутри |
|---|---|---|---|
| `data/profile.json` | `build-profile.ts` (только с `--force`) | **владелец, руками** | вес каждого тега 0..1 по каждому из четырёх бакетов, стоп-теги, веса лейблов, глобальный список hard-reject тегов |
| `data/location-vocabulary.json` | `build-profile.ts` (только с `--force-locations`) | **владелец, руками** | список городов/стран, которые вычитаются из тегов как шум (не путать город с жанром) |
| `data/neighbors.json` | `neighbors.ts` (еженедельно) | **бот** | до 40 «соседей по вкусу» (fan_id, вес близости, их коллекция) |
| `data/state.json` | `daily.ts` (ежедневно, и на каждое нажатие кнопки) | **бот** | что уже показано/опубликовано, штрафы за скипанные теги, offset Telegram-апдейтов, `message_id` живых карточек и служебных уведомлений (под снос следующим прогоном) |

`profile.json` и `location-vocabulary.json` — единственные два файла, которые
имеет смысл редактировать руками. `neighbors.json` и `state.json` —
машинно-генерируемые, руками их лучше не трогать: `daily.ts` пишет
`state.json` буквально на каждое нажатие кнопки, а не только в конце
прогона, так что ручная правка рискует разъехаться с тем, что боту прислал
Telegram.

## Как поменять вкус

Два способа, от быстрого к капитальному:

1. **Точечная правка.** Открыть `data/profile.json` и руками поправить вес
   тега или дописать/убрать что-то из `stopTags` нужного бакета. Изменение
   вступает в силу со следующего запуска `daily.ts`, пересборка не нужна.
2. **Капитальная правка.** Отредактировать `seedTags` бакета в
   `src/profile/buckets.ts` (какие теги вообще относят релиз к бакету) и
   перезапустить `npm run build-profile -- --force` — это пересчитает веса
   и стоп-теги заново по всей коллекции. Нужно, если жанр стабильно
   тегируется Bandcamp иначе, чем ожидалось, а не просто нужно подправить
   один вес.

Скипы в Telegram копятся автоматически в `data/state.json` → `feedbackTags`
(тег → сколько раз что-то с этим тегом скипнули) — это самозатухающий сигнал
(штраф ограничен потолком в `src/profile/score.ts`, `FEEDBACK_PENALTY_CAP`),
не файл для ручной правки, но полезно иногда посмотреть, что стабильно
скипается:

```bash
node --import tsx -e "
const s = JSON.parse(await (await import('node:fs/promises')).readFile('data/state.json','utf8'));
console.log(Object.entries(s.feedbackTags).sort((a,b)=>b[1]-a[1]).slice(0,20));
"
```

Тег со счётчиком 3+, который владелец подтверждает как «не моё», имеет смысл
перенести руками в `stopTags` нужного бакета в `data/profile.json` — тогда
он не просто штрафует, а активно отбраковывает (см. `STRONG_MATCH` в
`src/profile/score.ts` — сильное совпадение по-прежнему переживёт случайный
стоп-тег, слабое — нет).

**`stopTags` vs `hardRejectTags`.** `data/profile.json` содержит ещё одно
поле верхнего уровня — `hardRejectTags: string[]`, общее на все четыре
бакета (не внутри `buckets.*`). Это не более строгий стоп-тег, а другой
механизм: `stopTags` штрафует соседний ЖАНР (сильное совпадение переживает
случайный стоп-тег — это правильно, релиз соседнего жанра всё ещё может
быть тем, что хочет владелец), а `hardRejectTags` отбраковывает объект
НЕВЕРНОГО ТИПА безусловно, независимо от силы совпадения — сборник многих
артистов вместо релиза одного не становится желанным ни при каком наборе
жанровых тегов. Сейчас список — компиляции во всех написаниях, которые
реально встречаются на Bandcamp (`compilation`, `compilations`, `various
artists`, `va`, `sampler`, `label sampler`, `mixtape`); дописывать туда
жанр — не по адресу, для жанров есть `stopTags`. Правка вступает в силу со
следующего запуска `daily.ts`, как и правка `stopTags`. При пересборке
профиля (`npm run build-profile -- --force`) значение переносится из уже
существующего файла вперёд — `buildProfile()` не умеет вывести его из
данных коллекции, это чистая ручная настройка (см. комментарий у
`Profile.hardRejectTags` в `src/profile/build.ts`).

## Как добавить канал (пятый бакет)

1. Создать канал в Telegram, добавить бота администратором с правом
   «Публикация сообщений».
2. Дописать новую запись в `BUCKETS` в `src/profile/buckets.ts`: `id`,
   `channelTitle`, `channelEnv` (имя будущей секреты, например
   `POWERVIOLENCE_CHANNEL_ID`) и `seedTags`.
3. Узнать `chat_id` канала (переслать любое сообщение из канала боту и взять
   `forward_from_chat.id`, либо `@username` для публичного канала) и завести
   секрет: `gh secret set POWERVIOLENCE_CHANNEL_ID`.
4. **Дописать секрет в `.github/workflows/daily.yml`** — вручную, в блок
   `env:` шага «Подобрать релизы и дождаться апрува». Код (`loadConfig` в
   `src/pipeline/daily.ts`) сам вычисляет список нужных переменных из
   `BUCKETS`, но GitHub Actions YAML так не умеет — секрет, которого нет в
   `env:` шага, просто не долетит до процесса, даже если он заведён в
   настройках репозитория. Без этого шага пятый бакет упадёт на
   `не заданы переменные окружения: POWERVIOLENCE_CHANNEL_ID`.
5. Пересобрать профиль: `npm run build-profile -- --force` — иначе у нового
   бакета не будет записи в `data/profile.json` вовсе. `runDaily` (см.
   `src/pipeline/daily.ts`) обращается к `profile.buckets[bucket.id]`, для
   такого бакета это `undefined` — попытка использовать его падает,
   per-bucket `try/catch` в цикле по `BUCKETS` ловит это и пропускает бакет
   на весь день с `console.error` в лог (`daily: сбор кандидатов бакета …
   упал, бакет пропущен на сегодня`). Бакет не «промолчит» тихо и не
   «будет судить по seedTags напрямую» — до пересборки он не даёт вообще
   ничего, с явной ошибкой в логе прогона.

## Когда бакет притих

Если канал давно ничего не публикует, порядок диагностики:

1. **Посмотреть, что бот вообще предлагал.** В личке от бота должны быть
   либо карточки, либо служебное сообщение вида «‹канал›: сегодня без
   карточек» с уточнением — «нечего было предложить» (пул пуст: подписки/
   хаб Discover ничего не нашли) или «кандидаты были, но профиль отбраковал
   всё» (второе — повод смотреть профиль, первое обычно означает, что
   жанр просто редко выходит).
2. **Свериться с выводом `build-profile`.** Он предупреждает в консоли, если
   у бакета мало релизов (`releaseCount`) или мало тегов, переживших порог
   совпадения — тонкий профиль отбраковывает почти всё подряд. Лечится
   расширением `seedTags` в `src/profile/buckets.ts`, если в коллекции
   релизы жанра есть, но тегированы иначе, либо ручной правкой весов прямо
   в `data/profile.json`.
3. **Проверить `feedbackTags`** (см. раздел выше про смену вкуса) — не
   штрафуется ли случайно опорный тег бакета через смежный тег, который
   Bandcamp вешает почти на всё в жанре.
4. **Проверить `stopTags`** в `data/profile.json` на предмет
   гиперопеки — стоп-тег, случайно совпадающий с чем-то массовым в самом
   жанре, топит бакет целиком (см. `STRONG_MATCH`/`stopHits` в
   `src/profile/score.ts`: спасает только очень сильное совпадение).

## Секреты

Шесть переменных в GitHub Secrets — токен бота, чат владельца и по одному
`chat_id` на каждый из четырёх каналов:

```
TELEGRAM_BOT_TOKEN
OWNER_CHAT_ID
CRUST_CHANNEL_ID
DEATH_METAL_CHANNEL_ID
HARDCORE_PUNK_CHANNEL_ID
BLACK_METAL_CHANNEL_ID
```

```bash
gh auth switch --user MishaKolotov
gh secret set TELEGRAM_BOT_TOKEN
gh secret set OWNER_CHAT_ID
gh secret set CRUST_CHANNEL_ID
gh secret set DEATH_METAL_CHANNEL_ID
gh secret set HARDCORE_PUNK_CHANNEL_ID
gh secret set BLACK_METAL_CHANNEL_ID
```

Каждая команда спрашивает значение в интерактивном вводе — в аргументы
командной строки не писать.

**Локальный запуск.** Те же шесть имён лежат в `.env` в корне проекта
(файл в `.gitignore`, в репозиторий не уезжает). В CI переменные приходят
из Secrets, поэтому npm-скрипт их не подхватывает сам — локально запускать
надо с явным флагом:

```bash
node --import tsx --env-file=.env bin/daily.ts
```

Окно ожидания апрува задаётся переменной `LISTEN_MINUTES` (в CI — 120).
Для быстрой проверки удобно короткое:

```bash
LISTEN_MINUTES=10 node --import tsx --env-file=.env bin/daily.ts
```

Если `.env` потерялся, `chat_id` каналов достаются заново так: написать
что-нибудь в каждом канале (бот в них админ и видит публикации) и прочитать
`getUpdates` — id придут в поле `chat.id`.

Ничего секретного в самом репозитории не хранится: `data/*.json` несёт
только теги, веса, URL и заголовки релизов — публичные данные Bandcamp,
токены и chat_id туда никогда не попадают, они целиком живут в GitHub
Secrets и переменных окружения.

## CI (GitHub Actions)

| Workflow | Триггер | Что делает |
|---|---|---|
| `test.yml` | `push`, `pull_request` | `npm test` + `npx tsc --noEmit` |
| `daily.yml` | cron `0 6 * * *` (09:00 МСК) + `workflow_dispatch` | `bin/daily.ts`, коммитит `data/state.json` |
| `neighbors-weekly.yml` | cron `0 3 * * 1` (понедельник) + `workflow_dispatch` | `bin/neighbors.ts --force`, коммитит `data/neighbors.json` |

Оба джоба, пишущих в `data/`, состоят в общей concurrency-группе
`bandcamp-daily-data-write` — не запускаются одновременно друг с другом
(и с самими собой при повторном `workflow_dispatch`), а сохраняют
состояние через `fetch` + `rebase` + повтор пуша, а не голым `git push`:
если за время прогона (у `daily` — до трёх часов) владелец руками
запушил правку `data/profile.json`, коммит бота просто переустанавливается
поверх, а не молча теряется и не затирает чужое force-пушем. Оба джоба
коммитят строго свой файл (`state.json` / `neighbors.json`) — ручные файлы
(`profile.json`, `location-vocabulary.json`) эти workflow вообще не трогают.

Дисковый кэш страниц релизов (`.cache/`) в CI не переносится между
запусками: `neighbors.ts` его не использует вовсе, а `daily.ts` даже с
холодным кэшем укладывается в таймаут с большим запасом — холодный старт
стоит несколько минут сети, не поломку. Таскать через `actions/cache`
блоб, который на локальной машине уже перевалил за 400 МБ и продолжает
расти (страницы кэшируются навсегда), обошлось бы дороже редких минут
экономии, да ещё и конкурировало бы за общий с `test.yml` лимит кэша
GitHub на 10 ГБ на репозиторий.

Репозиторий должен быть публичным: Actions minutes приватного репозитория
не покрыли бы ежедневный ~2-часовой джоб на постоянной основе.

## Приватность публичного репозитория

Что узнает случайный читатель кода:

- **Bandcamp-личность владельца.** `bin/*.ts` хардкодят `fan_id = 7566215`
  (username `gigamike666`) — но это тот же id, что открыто виден на публичной
  странице `bandcamp.com/gigamike666`, ничего нового не раскрывает.
- **Детальный музыкальный вкус.** `data/profile.json` — это, по сути, читаемый
  дамп того, что нравится владельцу: веса тегов, лейблов, стоп-теги (что
  считается «не тем»). Не секрет, но куда подробнее, чем обычно выкладывают
  напоказ.
- **Числовые fan_id посторонних людей.** `data/neighbors.json` называет
  fan_id (не username) до 40 других Bandcamp-пользователей, чьи коллекции
  пересекаются с коллекцией владельца — это уже не про владельца, а про
  случайных третьих лиц, хоть их коллекции на Bandcamp и так публичны по
  умолчанию.
- **Токенов, паролей, chat_id — нет.** Проверено: секреты нигде не
  захардкожены, `data/state.json` (после первого прогона) несёт только
  URL/теги/заголовки релизов и внутренний offset Telegram-апдейтов
  (`lastUpdateId` — обычный счётчик, не секрет).

## Тесты

```bash
npm test          # node:test, 263 теста на момент написания
npx tsc --noEmit  # типы
```

Сеть в тестах не используется вообще: HTTP-клиент подменяется инъекцией
`fetchImpl`, парсеры проверяются на сохранённых фикстурах в
`test/fixtures/`.
