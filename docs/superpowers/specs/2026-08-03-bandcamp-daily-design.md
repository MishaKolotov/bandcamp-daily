# Bandcamp Daily — три телеграм-канала с ежедневными находками

Дата: 2026-08-03
Статус: дизайн утверждён, план реализации не написан

## Задача

Каждый день находить по одному лучшему релизу в трёх жанрах — crust, death metal, hardcore punk — исходя из личного вкуса владельца (Bandcamp-фанат `gigamike666`, fan_id `7566215`), и после ручного апрува публиковать в три телеграм-канала:

- `DEATH METAL DAILY`
- `CRUST DAILY`
- `HARDCORE PUNK DAILY`

В каждом канале ежедневно два поста: свежий релиз (не старше 7 дней) и откопанное из архива (релиз любого года, которого нет в коллекции и вишлисте).

## Исходные данные

Проверено запросом на этапе дизайна:

- страница `https://bandcamp.com/gigamike666` публична, отдаёт `data-blob` без авторизации;
- в коллекции 223 релиза, доступен вишлист, 45 подписок на группы/лейблы, 23 подписки на других фанатов;
- постраничная выборка коллекции — `POST https://bandcamp.com/api/fancollection/1/collection_items` с `fan_id`, `older_than_token`, `count`;
- в объекте релиза есть `item_title`, `band_name`, `band_id`, `item_url`, `url_hints.subdomain` (= лейбл), `also_collected_count`, `item_art_id`;
- жанровых тегов в коллекционном объекте нет — теги берутся со страницы самого альбома.

## Архитектурные решения

| Решение | Выбор | Причина |
|---|---|---|
| Что считать «лучшим» | Гибрид: свежак + архивное открытие | Свежак держит канал живым, архив даёт глубину |
| Как матчить вкус | Свежак — по тегам и подпискам, архив — по соседям-фанатам | Новый релиз ещё никем не куплен, коллаборативка его не видит |
| Хостинг | GitHub Actions cron | Бесплатно, состояние в JSON-файлах репо, без БД и сервера |
| Публикация | Ручной апрув кнопками в личке | Алгоритм на старте сырой, в канал не должно улетать случайное |
| Ботов | Один на три канала | Каналы различаются только `chat_id` |
| Видимость репо | Публичный | Приватному дают 2000 минут Actions в месяц, слушатель кнопок съедает 3600 |

## Компоненты

### 1. `src/bandcamp` — клиент

Отвечает за всё общение с Bandcamp и ничего не знает про вкус и Telegram.

- `fetchCollection(fanId)` / `fetchWishlist(fanId)` — постраничный обход `collection_items` до конца.
- `fetchFollowedBands(fanId)` — список подписок.
- `fetchAlbum(url)` — страница релиза: теги, лейбл, год, страна, дата публикации.
- `digDeeper(tag, sort)` — тег-хабы Bandcamp, источник свежих кандидатов.
- `fetchAlbumFans(albumUrl)` — фанаты, купившие релиз; вход в граф соседей.

Дисковый кэш: страница альбома читается один раз и больше не запрашивается никогда. Между сетевыми запросами пауза, User-Agent осмысленный. Разовая сборка профиля — около 250 запросов, ежедневный запуск — несколько десятков.

### 2. `src/profile` — вкус

- `buildProfile()` — разовый (и по требованию повторяемый) скрипт: коллекция + вишлист + подписки → частоты тегов, лейблов, стран.
  - Вишлист и недавние добавления весят больше старых покупок: это актуальный вкус.
  - Кластеризация в три бакета вокруг опорных тегов; соседние теги (d-beat, stenchcore, powerviolence, grindcore, death-doom, sludge, raw punk и т.п.) попадают в бакет по фактической встречаемости рядом в коллекции, а не по списку из головы.
  - Антипрофиль: теги, живущие в тех же хабах, но отсутствующие у владельца (deathcore, melodeath, symphonic, metalcore, beatdown) — идут в штраф.
- Результат — `data/profile.json`: веса тегов по бакетам, веса лейблов и стран, стоп-теги.
- **Файл утверждается человеком и правится руками.** Автоматического переобучения профиля нет; ежедневный запуск читает его как есть.
- `score(candidate, bucket)` — чистая функция без сети: совпадение тегов − штраф за стоп-теги + бонус за знакомый лейбл/страну + слабый логарифмический вклад `also_collected_count`.

### 3. `src/pipeline` — отбор

Для каждого бакета:

- **свежак** — объединение `digDeeper(tag, date)` по тегам бакета и релизов подписанных групп/лейблов моложе 7 дней;
- **архив** — покупки соседей по вкусу минус коллекция и вишлист владельца.

Соседи считаются отдельной недельной джобой (`neighbors-weekly.yml`): по релизам коллекции собираются другие фанаты, для каждого считается пересечение с коллекцией владельца, топ сохраняется в `data/neighbors.json`. Ежедневный запуск только читает этот файл.

Дальше: скоринг, отсев всего, что есть в `data/seen.json`, сортировка, взятие лучшего.

### 4. `src/telegram` — общение

- Отправка карточки: обложка, `Артист — Альбом`, теги, лейбл / страна / год, строка «почему это тебе» (совпавшие теги либо «соседи с 40% пересечением коллекции»), ссылка на Bandcamp.
- Инлайн-кнопки: `📢 В канал`, `⏭ Скип`, `🔄 Другой кандидат`.
- `📢` публикует в соответствующий канал и пишет релиз в `data/posted.json`.
- `⏭` и `🔄` пишут релиз в `data/feedback.json` — теги и лейбл этого релиза получают небольшой минус при следующем скоринге.
- Всё показанное в любом исходе попадает в `data/seen.json` и повторно не предлагается.

**Ловля нажатий без сервера.** После отправки карточек тот же запуск GitHub Actions два часа опрашивает `getUpdates` и обрабатывает нажатия. Если владелец не успел — Telegram держит очередь обновлений до 24 часов, и следующий утренний запуск первым делом её разгребает. Вебхук и постоянный хост не нужны.

## Поток данных

```
build-profile (разово)     collection + wishlist + follows → album pages → profile.json
neighbors-weekly (раз/нед) collection → album fans → пересечения → neighbors.json
daily (ежедневно 09:00 МСК)
    drain getUpdates → обработка вчерашних кнопок
    для каждого бакета:
        свежак:  digDeeper + follows → фильтр 7 дней
        архив:   neighbors.json → их покупки
        score → минус seen.json → топ-1
    отправка до 6 карточек в личку
    2 часа слушать кнопки → публикация в каналы
```

## Хранение состояния

Всё в репозитории, коммитится джобой в конце запуска:

| Файл | Содержимое |
|---|---|
| `data/profile.json` | веса тегов, лейблов, стран, стоп-теги |
| `data/neighbors.json` | соседи по вкусу и их вес |
| `data/state.json` | показанное, опубликованное, скипы и их влияние на скор, offset Telegram |

Секреты (`TELEGRAM_BOT_TOKEN`, `OWNER_CHAT_ID`, три `CHANNEL_ID`) — в GitHub Secrets, в репозитории отсутствуют.

## Тестирование

Node 20 + TypeScript, тесты на `node:test`.

- Парсеры страниц и API-ответов тестируются на сохранённых фикстурах; сеть в тестах не дёргается.
- `score()` — чистая функция, покрывается таблицей случаев: релиз со стоп-тегом проигрывает, знакомый лейбл добавляет вес, хайповый но чужой по тегам релиз не побеждает.
- Пайплайн тестируется на подменённом клиенте Bandcamp.
- Логика кнопок тестируется на синтетических апдейтах Telegram.

## Обработка ошибок

- Разметка Bandcamp изменилась → падает разбор конкретного релиза, кандидат выбрасывается, запуск продолжается.
- По бакету не нашлось кандидатов → в личку приходит «сегодня по CRUST пусто», а не тишина.
- Telegram вернул ошибку → ретрай с паузой; при повторной неудаче джоба падает, GitHub присылает письмо.
- Bandcamp начал отдавать 429 → увеличенная пауза и остановка сбора, работа с тем, что успели набрать.

## Границы

Не делаем: веб-интерфейса, базы данных, автопубликации без апрува, автоматического переобучения профиля, поддержки других жанров и каналов, скачивания музыки.
